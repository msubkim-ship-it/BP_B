## Keep — 유지할 것

> 교육·프로젝트 과정에서 **효과적이었던** 프롬프팅, 습관, 협업 방식을 적습니다.

1. Mom Test 인터뷰를 시작할 때 규칙을 먼저 선언했더니 AI가 솔루션을 끼워 넣지 않고, 「계산기를 가장 많이 쓴다」→「단위 이름 헷갈림」→「mm를 m로 잘못 씀」처럼 불편 중심 답을 끌어냈다. 문제 정의가 훨씬 선명해졌다.
2. TDD 작업은 `Phase: red | Layer: entity | Track: Logic`처럼 맥락을 붙인 슬래시 프롬프트(`/red-test-plan`, `/golden-master`, `/refactor-smell`)로 넘겼더니, AI가 범위 밖 구현(GREEN·REFACTOR)을 덜 섞었다.
3. 한 번에 한 단계만 요청하는 습관이 잘 맞았다. `/red-test-plan`(표만) → `/red-skeleton`(코드만) → GREEN처럼 나누니, 내가 검토할 산출물이 명확해졌다.
4. 단계가 끝날 때마다 Report + Transcript Export를 남겼더니, 나중에 Golden Master·브랜치 되돌리기처럼 막혔을 때 내가 무엇을 요청했는지 다시 추적할 수 있었다.

---

## Problem — 문제점

> **막혔던 점**, AI 활용의 어려움, 오해, 불편, 아쉬움을 솔직히 적습니다. (비난이 아닌 성찰)

1. Golden Master를 추가할 때 GREEN인지 REFACTOR 직전인지 먼저 헷갈렸다. 개념을 정리하기 전에 `/golden-master`를 실행해서, 왜 지금 이 단계인지 스스로 설명하기 어려웠다.
2. REFACTOR를 서두르다 브랜치가 꼬였고, input_parser/registry 추출을 되돌리는 데 시간을 썼다. Golden Master 기준선이 있는 브랜치인지 확인하지 않고 작업을 시작한 내 선택이 원인이었다.
3. spec 마무리 때 문서·골격·`.cursorrules`·Skill을 한꺼번에 쌓다 보니, 커밋을 어떻게 나눌지 고민하는 시간이 길어졌다. AI가 제안한 구조를 충분히 읽기 전에 「응 해줘」로 넘긴 순간도 있었다.
4. 동료 PR 5건을 한 메시지에 몰아서 리뷰를 요청했다. AI가 잘 정리해 주긴 했지만, 각 PR의 설계 차이를 내 말로 비교·판단하기는 어려웠다.

## Try — 시도할 것

> 다음 프로젝트·학습에서 **바꿔볼 구체적 행동**을 적습니다.

1. Golden Master·REFACTOR에 들어가기 전에, 채팅 맨 위에 `RED → GREEN → Golden Master → REFACTOR` 한 줄을 적고 「지금은 ○○ 단계」라고 선언한 뒤 시작하겠다.
2. REFACTOR는 `/refactor-smell` 표에서 P0 후보만 골라 `/refactor-safe`를 한 건씩 실행하고, 매번 pytest + golden matched를 내가 직접 확인한 다음 다음 후보로 넘기겠다.
3. 브랜치를 바꾸거나 되돌리기 전에 `git branch` + pytest 결과를 체크리스트로 확인하겠다. (Golden Master 커밋이 포함된 브랜치인지 먼저 본다.)
4. 페어 작업이나 팀 리뷰 전에는 프롬프트 초안(Phase·금지·완료 조건)을 먼저 공유하고, 실행은 그다음에 하겠다.
