# BP_B — KPT 팀 회고

> **Cursor AI 프롬프팅 응용 교육**을 마친 팀이, **KPT** 방법론으로 각자의 경험을 구조화하고 공유하는 저장소입니다.

---

## 이 저장소의 목적

| ✅ 하는 것 | ❌ 하지 않는 것 |
|-----------|----------------|
| 나의 학습·협업·프롬프팅 경험 **자기 성찰** | 코드·아키텍처·TC 상세 기술 |
| Cursor AI와 일한 **방식·태도·깨달음** 정리 | 프로젝트 구현 내용 나열 |
| 팀원 각자의 관점 **수집 → 발표용 취합** | 기술 문서·설계서 대체 |

실습은 [UnitConverter_07](https://github.com/msubkim-ship-it/UnitConverter_07)을 매개로 진행되었지만,  
**회고의 주제는 “프로젝트 결과”가 아니라 “나는 AI와 어떻게 일했고, 무엇을 배웠는가”** 입니다.

---

## KPT 방법론

짧은 회고 프레임입니다. 발표 전에 각자 같은 구조로 생각을 정리합니다.

| 구분 | 의미 | Cursor 교육 맥락에서의 질문 |
|------|------|---------------------------|
| **K**eep | 유지할 것 | 효과적이었던 **프롬프트·습관·협업 방식**은? |
| **P**roblem | 문제점 | 막혔던 점, AI에 **과도하게 맡긴** 부분, 오해·불편은? |
| **T**ry | 시도할 것 | 다음에는 **프롬프팅·검증·소통**을 어떻게 바꿀 것인가? |

## 회고 작성 가이드

### 초점 영역 (이 중 2~3가지를 골라 쓰면 충분합니다)

- **프롬프트 설계** — 지시의 명확성, 맥락 제공, 단계 나누기, 제약 전달
- **AI와의 역할 분담** — 내가 판단한 것 vs AI에 맡긴 것, 검증·리뷰 습관
- **학습·성장** — 교육 전후 인식 변화, 새로 익힌 협업 패턴
- **팀 협업** — 페어 작업, 리뷰, 의견 조율, AI 활용 공유
- **어려웠던 순간** — 기대와 다른 결과, 재시도, 포기하지 않은 이유

### 작성 원칙

1. **1인당 Keep / Problem / Try 각 2~4개** — 항목이 많을수록 좋지 않습니다.
2. **구체적 상황 1~2문장** + **느낀 점·배운 점** — “pytest 29 passed” 같은 성과 수치보다 **나의 경험**을 씁니다.
3. Problem은 **비난이 아닌 성찰** — 동료·AI·교육을 탓하기보다 “내가 어떤 선택을 했는가”에 초점.
4. Try는 **다음에 실행 가능한 행동** — “더 잘하겠다”보다 “다음엔 ○○할 때 △△하겠다”.

### 예시 (톤 참고용)

```markdown
### Keep
- 작업 전에 “코드 수정 금지, 리뷰만”처럼 **역할을 먼저 선언**하니 AI가 불필요한 diff를 덜 냈다.
- 막히면 바로 답을 요구하지 않고 **“왜 실패했는지 단계별로 설명해줘”** 로 전환해 스스로 이해하는 시간이 늘었다.

### Problem
- 한 번에 너무 많은 요구를 넣어 **AI 답변이 산만**해졌고, 나도 무엇을 검토해야 할지 놓쳤다.
- AI가 제안한 구조를 **충분히 이해하지 않고 수용**한 순간이 있어, 나중에 팀 리뷰에서 되돌리느라 시간을 썼다.

### Try
- 다음에는 요청을 **한 가지 Phase(예: RED만)** 로 쪼개고, 각 단계마다 내가 직접 확인할 체크리스트를 적겠다.
- 페어와 **프롬프트 초안을 먼저 공유**한 뒤 실행하겠다.
```

## 제출 워크플로

```text
1. main에서 브랜치 생성
2. reviews/ 아래 본인 KPT md 작성
3. push 후 (선택) PR 또는 팀 채널에 공유
4. 취합 담당자가 main에 팀 요약본 반영 → 발표
```

### 1. 브랜치 생성

```bash
git checkout main
git pull origin main
git checkout -b kpt/이름-영문또는로마자
```

| 팀원 | 브랜치 예시 | 파일명 |
|------|------------|--------|
| 김명섭 | `kpt/myeongsub-kim` | `reviews/kpt-김명섭.md` |
| 김민주 | `kpt/minju-kim` | `reviews/kpt-김민주.md` |
| 김소민 | `kpt-somin-kim` | `reviews/kpt-김소민.md` |
| 김연우 | `kpt/yeonwoo-kim` | `reviews/kpt-김연우.md` |
| 김정균 | `kpt/jeonggyun-kim` | `reviews/kpt-김정균.md` |
| 김준호 | `kpt/junho-kim` | `reviews/kpt-김준호.md` |

> 브랜치명은 팀 내 합의로 통일해도 됩니다. **파일명은 `reviews/kpt-{이름}.md` 형식**을 권장합니다.

### 2. 회고 작성

템플릿을 복사해 작성합니다.

```bash
cp KPT_TEMPLATE.md reviews/kpt-본인이름.md
```

### 3. 업로드

```bash
git add reviews/kpt-본인이름.md
git commit -m "Add KPT retrospective by {이름}"
git push -u origin kpt/본인브랜치
```

### 4. 취합 (발표 담당: 김명섭)

| 단계 | 담당 | 산출물 |
|------|------|--------|
| 개인 제출 | 각 팀원 | `reviews/kpt-{이름}.md` |
| 취합·요약 | 김명섭 | `summary/kpt-team-summary.md` (main) |
| 발표 | 팀 | 요약본 기반 1시간 회고·발표 |

취합 시 **개인 회고 전문을 그대로 붙이지 않고**, 팀 공통 Keep / Problem / Try와 대표 인용을 묶어 발표용으로 정리합니다.

```text
BP_B/
```

## 제출 체크리스트

개인 회고 업로드 전에 확인합니다.

- [ ] `reviews/kpt-{본인이름}.md` 경로·파일명 준수
- [ ] Keep / Problem / Try **모두 작성** (각 2개 이상)
- [ ] **프롬프팅·AI 협업·학습 경험** 중심 (코드·TC 상세 최소화)
- [ ] Try가 **다음 행동**으로 구체적
- [ ] 팀원 실명·작성일 기재
