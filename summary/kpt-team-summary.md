## 1. Keep — 팀이 유지하고 싶은 것

> **한 줄:** 단계를 나누고, 규칙을 고정하고, 기록을 남기면 Agent와 TDD가 잘 맞았다.

### 1-1. 프롬프트·워크플로

| 공통 패턴 | 팀 경험 |
|-----------|---------|
| **단계·Phase 분리** | RED / GREEN / REFACTOR를 한 번에 요청하지 않고, 「지금은 RED만」「표만」「코드만」처럼 범위를 좁히니 AI 답변이 집중됐다. (김민주, 김연우, 김소민) |
| **맥락 선언** | `Phase: red \| Layer: entity`처럼 슬래시 커맨드·ARRR 단계를 먼저 밝히면 범위 밖 구현이 줄었다. (김민주, 김연우) |
| **반복 규약은 Rule로** | venv, pytest 경로 등 매번 채팅에 쓰지 않고 Rule·Skill로 옮기니 이후 단계에서 AI가 전제를 스스로 지켰다. (김민주, 김명섭) |

### 1-2. 학습·문서화

| 공통 패턴 | 팀 경험 |
|-----------|---------|
| **Report + Transcript** | 단계마다 보고서와 대화 기록을 짝으로 남기니, 다음 세션에서 맥락을 다시 설명하지 않아도 됐다. (김민주, 김연우, 김소민) |
| **Agent와 함께 학습** | 모르는 개념을 Agent에게 질문하며 이해를 쌓고, Rule·Skill·Command·Hook으로 작업 환경을 직접 구축할 수 있었다. (김명섭) |
| **요구·설계 선행** | Mom Test → 요구·설계 문서 → TDD 순으로 고정한 뒤 개발에 들어가니 방향이 흔들리지 않았다. (김연우, 김정균) |

### 1-3. TDD·리뷰

| 공통 패턴 | 팀 경험 |
|-----------|---------|
| **단계 게이트** | RED는 `pytest.fail`, GREEN은 최소 구현, skip/xfail 없이 진행하는 원칙이 전반적으로 지켜졌다. (김소민, 김정균) |
| **리팩터 1스멜 1커밋** | 스멜 우선순위 표 → 한 건씩 적용 → pytest 확인 패턴이 안정적이었다. (김정균) |
| **팀 리뷰 피드백** | 리뷰에서 잘된 점·개선점이 명확해 다음 수정 방향을 잡기 쉬웠다. (김준호, 김민주) |

### 대표 인용

- *「Phase와 Rule로 AI 작업 범위를 좁히면 속도가 났다.»* — 김민주  
- *「맥락·규칙·단계를 먼저 선언하고 한 번에 한 산출물만 요청하면 AI와 TDD가 잘 맞았다.»* — 김연우  
- *「Agent와 함께 끝까지 밀어붙이며 환경을 만들 수 있었다.»* — 김명섭

## 2. Problem — 팀이 겪은 어려움

> **한 줄:** AI는 빠르지만, **판단·구조·브랜치·리뷰**는 사람이 먼저 잡아야 했고, 그 부분이 가장 허들이었다.

### 2-1. 개념·판단

| 공통 이슈 | 팀 경험 |
|-----------|---------|
| **익숙하지 않은 개념·약어** | TDD, Dual-Track, ARRR, Golden Master 등 용어가 많아 실습과 이해를 동시에 따라잡기 어려웠다. (김명섭, 김준호) |
| **AI 제안을 이해 전 수용** | 테스트가 통과하거나 답이 나오면 구조 검증 없이 넘어갔다가, 팀 리뷰에서 되돌리는 경우가 있었다. (김민주, 김연우, 김명섭) |
| **모호한 요구·SSOT** | 출력 형식·단위 범위처럼 정답이 여러 개인 주제는 AI만으로 정리되지 않았고, 사람이 먼저 기준을 정해야 했다. (김민주) |
| **spec·설계 리뷰 자신감** | 문제 정의·구조·원칙을 사람이 확고하게 정하는 단계에서 스스로 판단하기 어려웠다. (김명섭) |

### 2-2. 프로세스·협업

| 공통 이슈 | 팀 경험 |
|-----------|---------|
| **브랜치·Phase 혼선** | red / green / staging / refactoring 역할을 혼동하거나, 한 PR에 여러 Phase가 섞여 리뷰 범위가 모호해졌다. (김소민, 김정균, 김연우) |
| **단계 혼동·서두른 REFACTOR** | Golden Master 시점을 헷갈리거나 기준선 확인 없이 리팩터를 시작해 브랜치가 꼬인 경험이 있었다. (김연우, 김정균) |
| **리뷰 맥락 전달 부족** | PR 본문이 비어 있거나, Report·Prompting을 따로 봐야 전체 흐름이 이해되는 경우가 있었다. (김소민) |
| **실질적 팀 리뷰 시간** | 협업·PR 형식이었으나 각자 진행에 가까워, 동료 리뷰보다 Agent 리뷰에 의존한 면이 있었다. (김명섭) |

### 2-3. 도구·역량

| 공통 이슈 | 팀 경험 |
|-----------|---------|
| **신규 툴 미숙** | Cursor·Agent 워크플로가 처음이라 사용법을 익히는 데 시간이 걸렸다. (김준호) |
| **Mom Test·페르소나** | 활용 방법이 익숙하지 않아 프롬프트에 충분히 반영하지 못했다. (김소민) |
| **환경 이슈** | git push SSL 등 환경 문제로 작업 흐름이 끊긴 적이 있었다. (김정균) |

### 대표 인용

- *「AI가 빠르게 만든 초안을 구조까지 검증하지 않은 게 아쉬웠다.»* — 김민주  
- *「브랜치·PR 범위 관리와 리뷰 맥락 전달에 아쉬움이 있었다.»* — 김소민  
- *「처음 사용하는 툴에 대한 미숙으로 헤맸다.»* — 김준호

## 3. Try — 팀이 다음에 시도할 것

> **한 줄:** **한 Phase · 한 산출물 · 한 검증**을 지키고, **사람이 먼저 판단**한 뒤 Agent는 실행에 맡긴다.

### 3-1. 프롬프팅·역할 분담

1. **요청은 「한 Phase + 한 Track + 완료 조건」으로 쪼갠다.**  
   예: 「red 브랜치, Logic Track만, pytest.fail 6건, skip 금지, 결과만 보여줘」 (김민주, 김연우)

2. **AI 코드 제안 전 「왜 이 구조인지」를 먼저 묻고, 이해한 뒤 적용한다.**  
   fixture·설정·예외 계층처럼 리팩터 비용이 큰 부분은 GREEN 직후 짧게라도 구조를 확인한다. (김민주)

3. **spec·SSOT·모호한 요구는 AI에 맡기기 전, 사람이 한 줄로 기준을 정한다.** (김민주, 김명섭)

4. **실행 전 페어·팀에 프롬프트 초안(Phase·금지·DoD)을 공유한다.** (김민주, 김연우, 김명섭)

### 3-2. TDD·브랜치·문서

1. **단계 진입 전 선언:** `RED → GREEN → Golden Master → REFACTOR` 중 「지금은 ○○」를 채팅 맨 위에 적는다. (김연우)

2. **브랜치·PR 체크리스트:** base branch 재확인, Phase별 커밋 분리, PR 본문에 목적·범위·Report 링크 포함. (김소민, 김정균)

3. **REFACTOR는 P0 스멜 1건씩 → pytest + golden 확인 → 다음.** 기준선 없이 smell부터 시작하지 않는다. (김연우, 김정균)

4. **단계 마감 시 Transcript Export를 DoD에 포함한다.** (김민주, 김소민)

### 3-3. 학습·역량

1. **SW 기본기(TDD·설계) 스터디를 Agent 활용과 병행한다.** (김명섭)

2. **C2C, Dual-Track TDD, ARRR을 반복 학습하며 나만의 체크리스트로 정리한다.** (김명섭)

3. **신규 툴·워크플로는 다른 프로젝트에서 직접 써 보며 경험을 쌓는다.** (김준호, 김소민)

4. **팀 공통 이슈(`__pycache__`, D-LOC 등)는 1-pager로 정리해 개인 리뷰 부담을 줄인다.** (김정균)

### 팀 Action Item (다음 1개만 선택 실행)

| 후보 | 담당 제안 |
|------|-----------|
| PR 본문 템플릿 도입 (목적·범위·Report 링크) | 김소민 Try → **팀 공통** |
| 브랜치 역할 1페이지 고정 | 김정균 Try → **팀 공통** |
| 프롬프트 초안 페어 공유 | 김민주·김연우 Try → **팀 공통** |

## 4. 마무리 — 발표 클로징 (30초)

이번 **Cursor AI를 활용한 소프트웨어 개발** 교육에서 팀은 공통적으로 다음을 확인했습니다.

- **Keep:** Phase 분리, Rule 고정, Report·Transcript 기록 — Agent와 TDD를 함께 쓰는 **방법**을 배웠다.
- **Problem:** 빠른 AI 답변 속에서 **구조 이해·브랜치 관리·사람 리뷰**가 병목이었다.
- **Try:** Agent는 **실행**, 사람은 **판단·검증·기록** — 이 역할 분담을 다음 프로젝트에 가져간다.

> *「Phase와 Rule로 범위를 좁히면 빨라지고, SSOT와 구조 같은 판단은 내가 먼저 확정하는 것이 안전했다.»*  
> — 팀 회고 종합 (김민주 인용 중심)
